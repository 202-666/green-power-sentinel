### 2.2 性能瓶颈分析

当前瓶颈明确在**综合评分模块的预提取循环**（29s / 41s = 71%）：
- 该循环遍历 43200 个时间点，逐点从各模块的 DataFrame 中提取分数并组装状态字典
- 持久性过滤与等级映射本身已是向量化（< 0.1s），瓶颈在数据组装

**优化方向**（见技术文档 §6.2）：
- 将各模块直接输出 NumPy 数组，跳过 dict 组装
- 或采用 Numba JIT 加速预提取循环

## 三、关键创新：持久性确认 + 后向回填

### 3.1 问题背景

Phase 3t 配置（consecutive N=20）已实现 F1=0.8340、正常数据零误报，但 Recall 卡在 81.79%。

**根因分析**（漏检诊断）：
- 故障段前 0-14 分钟，物理信号未充分发展
- 各模块 raw 检出呈间歇性（如 30min trend 在第 5 分钟触发，第 6-8 分钟因噪声回落，第 9 分钟再次触发）
- 严格连续持久性过滤（要求 20 个连续 yellow+）把这类间歇信号整段滤掉

### 3.2 解决方案：consecutive + backfill 组合

**核心创新**：在 consecutive N=20 严格过滤的基础上，增加"确认后向回填"机制。

```yaml
ensemble:
  persistence_filter: true
  persistence_mode: "consecutive"
  persistence_n: 20              # 严格连续 20 个 yellow+ 才确认
  persistence_backfill: 15       # 确认后向回填 15 个点
```

**backfill 物理依据**：
- 一旦某点被持久性过滤确认 yellow+，说明故障已发育到可检测水平
- 其前 15 分钟内的"弱信号"（任一模块 score > 0）属同一故障发育期
- 仅回填弱信号点，避免把纯噪声段误判为故障早期

**向量化实现**（ensemble_scorer.py L482-505）：
```python
# 反向 rolling sum：检查每个弱信号点 [i, i+backfill] 内是否有确认点
forward_count = (
    confirmed_series[::-1]
    .rolling(persistence_backfill + 1, min_periods=1)
    .sum()[::-1]
)
has_confirmed_ahead = forward_count.to_numpy() > 0
promote_mask = weak_signal_mask & ~confirmed_mask & has_confirmed_ahead
levels_arr[promote_mask] = "yellow"
```

### 3.3 效果对比

| 配置 | Recall | F1 | 正常 FP | 说明 |
|---|---|---|---|---|
| Phase 3t（consecutive N=20） | 81.79% | 0.8340 | 0 | 严格过滤，FP=0 但 Recall 不足 |
| Phase 3v（allow_single_module_alert） | 92.05% | 0.0198 | 35469 | FP 爆炸 |
| **W7 最终（consecutive + backfill=15）** | **91.03%** | **0.8864** | **0** | **backfill 恢复早期信号，FP 仍为 0** |

**关键结论**：backfill 机制将 Recall 从 81.79% 提升至 91.03%（+9.24%），同时保持正常数据零误报。这是物理可解释的优化，而非纯数值调参。

## 六、改进建议（后续优化方向）

### 6.1 短期（W8+，不影响验收）

1. **综合评分预提取循环优化**：当前 29s 瓶颈在逐点 Python 循环组装状态字典。建议各检测模块直接输出 NumPy 数组，跳过 dict 中转，预期可降至 < 2s
2. **炉排卡滞 FP 治理**：29 个 FP 集中在 furnace_pressure 正常波动段被 backfill 提升。可对 backfill 增加额外约束（如要求弱信号模块包含 correlation）
3. **ensemble 权重动态调整**：当前 `dynamic_weight: true` 仅为配置占位，实际权重仍固定。可基于规则历史匹配率（当前 R2 仅 18.9%）动态降低低匹配规则权重

### 6.2 中期（实时化方向）

1. **Numba/Cython 加速**：综合评分预提取循环可用 Numba JIT 加速，预期 29s → < 1s
2. **增量检测接口对接流式数据源**：`run_incremental_detection` 已实现，需对接 Kafka/MQTT 实时流
3. **动态基线阈值调优**：`trend_dynamic_threshold` 已实现，但 k=3.0 在 furnace_temperature 上阈值偏松（29.7 vs 固定 6.0），需按参数标定 k 值

### 6.3 长期（算法演进）

1. **ML 异常检测模型**：当前全规则驱动，可补充 Isolation Forest / Autoencoder 作为弱监督信号
2. **多设备联邦基线**：当前基线单设备计算，可扩展为同型号设备群联邦基线
3. **因果推理**：当前关联检测仅做时序同步，可引入 Granger 因果检验区分"相关"与"因果"
